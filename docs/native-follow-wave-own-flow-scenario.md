# 마스터 파형 추종과 슬레이브 슬롯 Flow · 통합 시험안

## 사용자 질문과 현재 상태

구현 상태 갱신: 아래 구현 전 범위 검토는 계획 당시 기록이다. `18233ae`의 한정 해제 뒤
세 구간 구현과 전체 2680개 검증을 마쳤으며, [구현 결과](native-wave-flow-implementation.md)에
결속했다. 새 실행 이미지도 준비·격리 대조를 마쳤고 두 역할 실기는 아직 시작하지 않았다.

사용자가 다시 명시한 질문은 두 가지다. (1) 역할 연결 상태에서 보고 파형을 누가
주도하는가. (2) 슬레이브가 자기 시간표의 서로 다른 Flow를 적용하고 변경할 수 있는가.
앞선 초안은 두 시간표에 같은 파형을 지정하여 첫 질문을 구분하지 못했다. 아래는 이를
바로잡은 설계이며, 양쪽에 서로 다른 파형·Flow를 지정하고 결과를 독립적으로 분류한다.
Sync와 Anti-Sync의 결과는 따로 기록한다. 실제 임펠러 위상·물리 수류량은 protocol 보고값만으로
증명하지 않는다. 보고 파형과 실제 파형을 동일시하지 않는다.

사용자는 필요한 질문을 한 현장 세션에 묶고 10분·15분 경계를 사용한 배포·실행을
요청했다. 현재 이미지는 이 계획을 구현하지 않는다. 기존 고정 Sync 계획은 서로 다른
파형 및 5분 시차를 가지므로 그대로 재실행하지 않는다. 현재 source 동결을 자동 해제하거나
소진된 구현 예외·이전 실기 권한을 재사용하는 문서가 아니다. 후속 한정 동결 해제 질문에
사용자가 "제발좀 한번에하라고 내가 승인했잔아 쫌 하자"로 재승인했으며,
새 열 파일 범위·두 operation 권한은 AGENTS의 별도 절과 정책 커밋에 결속한다.

직전 실기는 Sync 역할 진입 전에 종료됐다. durable 결과는
`experiment_failed_restored`, CLI 예외 표기는 `LinkageApplyError`다.
두 Pro의 원 시간표와 앱 준비 후 controls는 사후 fresh 2 pair에서 일치했다.
첫 Pro의 앱 준비 이전 TimerOFF와 원 서비스 재시작은 아직 완료로 기록하지 않는다.
직전 실기 결과를 먼저 보존·기록하며 원 예외를 추정해 새 코드를 만들지 않는다.

## 한 역할에서 두 질문을 구분하는 구성

아래 시각은 확정할 실행 기준 시각 T0로부터의 상대 시각이다. 실제 device-local 절대 시각,
준비 시간, 유효 표본 수·경계 제외 구간은 구현 검산 후 실행 전에 고정한다.
지금부터 자동으로 카운트다운이 시작됐다는 뜻이 아니다.

| 구간 | 마스터 시간표 | 슬레이브 시간표 | 질문 |
|---|---|---|---|
| T0부터 +10분 전 | Sine / Flow35 / F30 | Constant / Flow30 / wire F0 | slave가 보고하는 파형·Flow가 각각 어느 쪽과 일치하는가 |
| +10분부터 +15분 전 | Constant / Flow32 / wire F0 | Sine / Flow40 / F30 | 파형 선택과 자기 Flow30→40 변경을 같은 경계에서 구분 |
| +15분 이후 | Constant / Flow32 유지 | Sine / Flow35 / F30 | master 전환 없이 slave의 예약 Flow40→35만 변경되는가 |

위 표는 저장할 시간표이지 실제 슬레이브 출력을 단정한 표가 아니다.
master 파형 + 자기 Flow가 적용된다면 slave의 보고값은
Sine30 → Constant40 → Constant35가 된다. 이는 확인할 가설이며 PASS를 미리 정하지 않는다.

10분 경계 이후의 안정된 fresh 보고값은 다음처럼 구분한다.

| slave 보고값 | 해당 구간에서 지지되는 설명 |
|---|---|
| Constant40 | master 파형과 자기 슬롯 Flow의 조합 |
| Sine40 | 자기 슬롯 파형과 자기 슬롯 Flow의 조합 |
| Constant32 | master 파형·Flow 모두와 일치 |
| Sine32 | 자기 슬롯 파형과 master Flow의 조합 |
| 이전값 유지·기타·표본 부족 | 해당 관측 그대로 보존; 위 가설로 억지 분류하지 않음 |

연결 전 independent에서 두 원 시간표와 임시 시간표가 의도한 bytes인지 확인하고,
역할 진입 전후 raw·유효 Auto 필드를 보존한다. inactive manual Mode/Flow를 현재 출력으로
오인하지 않는다. 두 경계 주변에서는 유효한 새 표본과 시간 구간을 함께 대조한다.

10분 경계와 15분 경계는 같은 질문이 아니다. 10분 경계에서 slave40이 관측되어도
마스터 시계가 slave 갱신을 유발했다는 내부 인과까지 확정하지 않는다.
15분 경계에서는 slave35(자기 예약값), 40(직전값 유지), 32(마스터 값), 기타 값을
구분해서 보존한다. 표본 부족·지연 프레임·불일치는 UNKNOWN으로 남긴다.
슬레이브는 세 구간, 마스터는 두 구간이므로 전체 schedule image와 슬롯 구조도 기록한다.
이 구조 차이에 따른 모든 내부 구현 가설이 배제된다고 주장하지 않는다.

## 같은 현장 세션의 실행 순서

1. 직전 실행의 기록·현재 상태·남은 복원 의무를 확인한다. 현재 두 대 TimerON을 준비 상태로 이어 쓰되, 아래 앱 이전 원본과 이번 하네스 baseline을 구분해 보존한다.
2. Sync에서 위 세 구간을 한 번 관측하고 하네스가 소유한 기준선까지 복원한다.
3. 복원을 독립 확인한 뒤 Anti-Sync에서 같은 구성의 세 구간을 한 번 관측한다.
4. 원 시간표·controls·역할·서비스를 복원하고 앱 준비 이전 상태와 수용된 상태를 구분한다.

한 현장 세션이라는 것은 역할별 결과·저널·복구 권한을 하나로 혼합한다는 뜻이 아니다.
첫 역할에서 원복 실패·구체적 위험·새로운 실행 차단이 생기면 다음 역할을 자동 실행하지 않는다.
장비 기능에 대한 부정적 관측 자체는 실험 실패로 처리하지 않는다.

### 실행 전 결속과 최종 원복 목표

사용자가 다시 끝까지 진행하도록 지시한 뒤 14:36:10.689310–14:36:54.007851Z에
fresh2 pair를 보존했다. 묶음 `wave-flow-current.lBPhmkKa`, series SHA256
`31180b1d4cc2c02c2d0e926b177e1ee647215f96b46aab541ec37a2ce35dc573`이다.
두 대 ON/TimerON/independent·오류0이며 원432B 시간표와 각각 byte-exact다.
master의 현 Auto는 Sine45/F40, slave는 Sine65/F80이고 manual30/F32·40/F34는 비활성 저장값이다.
현재 TimerON은 앱 준비 이후 상태이지 앱 이전 원본이 아니다.

하네스는 각 operation 시작 때 snapshot한 두 대 TimerON·원 시간표·controls를 복원한다.
마지막 사용자 앱 원복 목표는 **first Pro TimerOFF / manual constant40 / Frequency34**다.
second는 TimerON·수용된 manual constant30/F32와 원 시간표를 유지하고 current slot은 그때 시각으로
확인한다. 첫 Pro의 중간 OFF→ON 왕복은 추가하지 않는다.
이전 실행의 마지막 앱 원복·서비스 복귀 의무와 이번 두 operation의 원복 의무는 별도로 기록한다.
최종 앱 토글 한 번이 실제로 양쪽 의무를 닫더라도 각 기록에 관측을 따로 덧붙인다.

### 두 역할의 logical 호출 회계

[기존 단회 표](native-sync-live-plan-2026-09-14.md#정상-경로의-write-회계)의 safe2·sentinel
forward2/restore2·field2·arm2·role2·보상 다섯 단계 각2를 그대로 사용한다.
Sync는 전진10+보상12=22이고, Anti-Sync는 slave Sync 중간 진입1이 추가되어 전진11+보상12=23이다.
Anti-Sync의 순서는 master → slave Sync 검증 → slave Anti-Sync이며 기존 경로만 사용한다.
이는 정상 경로 정적 logical 회계다. skip과 실패 분기는 별도이며 physical frame 수·성공 수가 아니다.
세 슬롯 구성도 전체432B image 한 번을 쓰므로 슬롯 수를 schedule write 횟수로 더하지 않는다.

실행 source는 `6978d2dadf0400958241dc7ebd638d4be04b4763`, image는
`200564aeeaa084e181c887a431149f9d672d443d9931e376475d720c58a506f1`로 고정한다.
원 서비스와 prior image는 보존한다. 각 wrapper는 별도 approval·exclusive run-invoked 표식을
남기고 preflight1회/run1회만 호출한다. 앞 intent는 덮이기 전에 별도 보존한다.
둘째 역할을 시작하는 자동 루프는 없으며 첫 회 원복·기술적 결과를 실제로 확인한 뒤 시작한다.

## 구현 전에 고정할 범위

현재 CLI/spec은 하나의 boundary와 두 구간 및 고정 signature로 역할·진입 경로를 선택한다.
새 세 구간·두 경계 계획은 설정 파일만 바꿔서 표현할 수 있다고 확인된 상태가 아니다.
새 계획의 signature, 두 역할 선택, 관측 결과 분류, 기존 기록의 로드·원복 의미를 함께
검토해야 한다. 기존 park 진입 예외를 일반 Async 경로로 조용히 확장하지 않는다.

변경 source·직접 테스트는 AGENTS에 열거한 열 파일로 한정하며 명시적 동결 해제의
별도 정책 커밋을 선행한다. 배포 요청만을 근거로 삼지 않고 후속 동결 해제 질문에 대한
사용자의 재승인과 구분해 기록한다.
legacy 동작·identity·출력 범위·single-write·journal·rollback·기존 timeout/retry는 보호한다.
새 fake를 펌웨어 답으로 쓰지 않는다. 오프라인 시험은 계획 구성과 기록·복구 계약만 검증한다.
실제 source/image·현재 현장 상태·복원 수단을 결속하기 전에는 새 device command를 보내지 않는다.

## 시간 예산 검산

새 계획만 role authority 1035초에서 기존 원복 reserve15초를 뺀 1020초 관측을 쓴다.
legacy 915/900초는 유지한다. outer는 기존 `min(1200, window+285)`라 1200초이며,
1035초 대비165초, 순수 관측1020초 대비180초 차이다. 이 차이를 물리 원복 성공 보장으로
해석하지 않는다. 구성 원복과 부모 원복은 별도 shield task를 끝까지 기다리고,
원복 write는 전진 expiry가 아닌 안전 인터록·기존 개별 I/O timeout으로 제한된다.
전진 만료나 취소가 원복 자체를 같은 1200초에서 자르지는 않지만,
통신·신원·안전 인터록 실패에 따른 recovery-required는 그대로 가능하다.

T0는 fresh 두 장비 중 늦은 시각의 **그 분 시작**으로 고정한다. 슬롯은 분 단위이므로
첫 실제 대기는9~10분이며, T1=T0+10분, T2=T0+15분이다. 실행 직전 첫 경계까지
520~600초가 남아 있어야 새 계획과 같은 lead 구간이다. 기존 CLI lead 계약은 유지한다.
epoch는 역할 ACK 뒤 시작하므로 준비 지연Δ만큼 W0는 줄고 W2는 늘어난다.
Δ=0·T0와 fresh 시각이 같을 때 아래 길이는 경계 끝점을 제외한 기하학적 길이다.

| 구간 | 경계 제외 후 범위 | 요구 |
|---|---|---|
| W0 | 첫 경계−60초 이전, 최대540초 | 새 pair10개·동일 보고값120초 |
| W1 | 첫 경계+60초부터 둘째 경계−60초까지,180초 | 새 pair2개 이상·30초 |
| W2 | 둘째 경계+60초 이후, epoch 끝까지 최소60초 | 새 pair2개 이상·30초 |

분 시작 반올림은 W0를 최대60초 줄이며 W2에는 그만큼 여유를 준다.
이 표는 네트워크 취득 지연을 없다고 가정한 창 계산이지 표본 확보 보장이 아니다.
새 monitor는 기존8초 취득·10초 pause를 바꾸지 않고 최대104회로 한정한다.
양쪽 장비 시각의 같은 분·전진을 확인하고 반복 시각 표본은 다시 세지 않는다.
경계 포함±60초는 raw에 남지만 안정 표본 수에 넣지 않는다.
표본 부족·충돌·raw 보존 실패는 전체 관측 완료로 승격하지 않는다.
