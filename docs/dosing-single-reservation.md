# 도징 외부 시간표와 채널별 다음 예약

## 구현 범위와 운용 상태

2026-10-02 서버와 HA Aqua 도징 화면에 비활성 상태로 배포했습니다.
시간표 활성화·실제 투여·투여량 실측은 진행하지 않았습니다.
기본 시간표는 비어 있으며 운영 시각과 투여량은 별도로 정합니다.
배포 증거와 보존 범위는 [배포 기록](runs/2026-10-02-ha-dosing-generator-deployment.md)에 있습니다.
소프트웨어 테스트는 장비 펌웨어의 실행·정지 또는 실투여량을 증명하지 않습니다.

전체 시간표와 템플릿은 호스트에 저장하고, 각 채널의 가까운 미래 예약 한 건만
기기의 `CH1SWTime` … `CH4SWTime`에 넣습니다. 예약량은 기존 앱 스키마의 정수
1–9999 범위이며 실제 계량 정확도는 채널 보정 및 실측으로 확인해야 합니다.
이 범위는 수조에 안전한 투여량을 뜻하지 않습니다.

## 편집과 활성화

- 템플릿 32개, 템플릿당 최대 384행, 채널 1–4.
- 시각·예약량·요일·기준일 기준 N일 간격, 전체량 균등 분할 생성.
- 생성한 분할은 정수 mL로 합계를 보존합니다. JSON 가져오기/내보내기와 복사를 지원합니다.
- 저장·불러오기·분할 생성은 **장비 송신 0회**입니다.
- 활성화는 저장본의 불변 해시를 실행본으로 선택합니다. 실행 중 편집·저장은 실행본을
  변경하지 않습니다. 교체는 일시정지 → 예약 해제 확인 → 새 저장본 활성화 순서입니다.
- 포함된 채널만 인계합니다. 해당 채널의 기존 시간표는 초기화 전 로컬 기록에 남기고,
  Timer를 끈 뒤 기존 이미지를 비웁니다. 포함되지 않은 채널은 그대로 둡니다.
- 원본 이미지는 현재 실행 기록에 남으며 다음 활성화 시 교체됩니다. 자동 복원하지 않습니다.
- 직접 제어와 외부 시간표의 충돌을 막습니다. 요청된 OFF는 시간표를 정지시키고 기존
  제어 경로로 넘깁니다. 실제 OFF 성공 여부는 그 경로의 응답/기록으로 확인해야 합니다.

## 자동 생성 사용법

채널 → 목표 기준 → 분배 방식 → 첫 투여 날짜와 시각 → 미리보기 순서로 입력합니다.
미리보기는 날짜별 예약량과 간격, 다음 주기 시작 또는 기간 종료를 보여줍니다.
계산 결과를 해당 채널 편집본에 반영한 뒤 저장하며, 활성화는 별도입니다.
다른 채널의 편집 일정과 현재 실행본은 미리보기 반영으로 바뀌지 않습니다.

| 입력 | 균등 분배 결과 |
|---|---|
| 하루 평균 1.5mL, 횟수 자동 | 2일간 총 3mL, 16시간마다 1mL씩 3회 |
| 하루 평균 0.3mL, 횟수 자동 | 10일간 총 3mL, 80시간마다 1mL씩 3회 |
| 3일간 총 30mL, 3회 | 24시간마다 10mL씩 3회 |
| 3일간 총 30mL, 한 번에 투여 | 지정한 날짜·시각에 30mL 1회 |

하루 평균 목표는 소수 둘째 자리까지 입력할 수 있습니다. 장치에 보내는 개별 예약량은
정수 mL이며, 소수 목표를 만족하는 최소 반복 기간을 유리수 연산으로 계산합니다.
횟수 자동은 1mL씩, 직접 지정은 같은 정수량·같은 분 단위 간격으로 나눕니다.
불가능한 조합은 반올림하지 않고 오류와 가능한 횟수를 표시합니다.
균등 계산은 첫 투여 시점부터 주기 끝 직전까지이며, 마지막 투여를 주기 끝에도
중복 배치하지 않습니다. 같은 패턴 반복을 끄면 기간 종료 후 다음 예약을 만들지 않습니다.

기간 총량은 정수 mL만 받습니다. 생성 계획은 채널당 하나이며 직접 작성한 같은 채널의
행과 중복 저장할 수 없습니다. 활성화 때 이미 지난 시각은 보충 투여하지 않습니다.
긴 기간에 걸친 평균량은 매일 소량 투여와 화학적으로 같다는 뜻이 아닙니다.
간격은 선택한 시간대의 현지 시각 기준이며 서머타임 구간의 실제 경과 시간은 다를 수 있습니다.

## 예약 처리

1. 현재부터 90초 이상 뒤의 다음 시각을 선택하며, 5분 이내에 들어오면 예약 준비를 시작합니다.
2. 채널 Timer OFF → 단일 예약 이미지 → Interval 0 → Timer ON 순서로 적용·검증합니다.
3. 각 단계의 ID와 진행 상태를 디스크에 먼저 저장합니다. 기존 장비 writer의 identity,
   lease, 권한, fsync journal 및 read-back 검증을 사용합니다.
4. ACK 누락 등 미종결 단계는 같은 ID로 새 상태를 조회합니다. 적용이 관측되면 다음 단계로,
   다르면 해당 시도를 종료하고 예약을 해제합니다. 이미 송신한 단계를 재송신하지 않습니다.
5. 조회 실패 시 2초 루프에서 재조회합니다. 성공이라고 처리하거나 새 ID로 우회하지 않습니다.
6. 시각이 지난 새 예약은 활성화하지 않습니다. 지나간 투여를 몰아서 보충하지 않습니다.
7. 설정된 정리 대기 시간이 지나면 예약 이미지를 비웁니다. 기본 5분은 **완료 측정값이 아닌
   정리 정책**입니다. 실제 운전 시간에 맞춰 정해야 합니다. 같은 채널의 행은 이 시간에
   추가 예약 준비 여유를 둬야 하며 저장 시 간격을 검사합니다.

일시정지 요청은 즉시 active를 해제하지만 장치 예약의 해제 확인까지 `clearing` 상태를
유지합니다. `paused`와 `clearing`, `waiting_device`를 같은 상태로 표시하지 않습니다.
재시작은 동일 journal을 재조회하며, 실행 잠금 획득 후 최신 부모 기록을 다시 읽습니다.

## 반드시 알아야 할 한계

**기기 슬롯은 진짜 일회성 예약이 아니라 매일 반복되는 시각 슬롯입니다.**
호스트나 네트워크가 장기간 중단되어 예약을 지우지 못하면 다음 날 같은 양이 반복될 수
있습니다. 이 설계는 정지 명령을 호스트가 직접 보내는 방식은 피하지만, 호스트 장애 때의
중복 투여까지 막는 하드웨어 만료 기능은 제공하지 않습니다.

장치 예약 확인은 설정값 확인일 뿐 실제 액체가 나왔다는 증거가 아닙니다. 화면과 기록은
`reservation_verified`와 `window_elapsed_unmeasured`를 구분하고 `delivered_ml`은 null입니다.
장치의 시계/시간대는 템플릿과 일치해야 합니다. 이 구현은 장치 시계를 읽어 검증하거나
자동 보정하지 않습니다. 앱의 별도 조작/전원 변경이 감지되면 외부 시간표를 정지합니다.

## 배포 시 연결 방법

기존 write-enabled `jebao-flow-local serve` 실행에 아래 옵션을 추가합니다.
논리 멤버는 설치 manifest의 도징기 멤버명이며 주소나 장비 ID를 넣지 않습니다.

```text
--dosing-scheduler-member <logical-dosing-member>
```

옵션이 없으면 기존 런타임은 변하지 않습니다. 영속 데이터는 기존 공유 hardware-safety
볼륨의 `dosing-single-reservation` 아래에 저장합니다. 이 볼륨을 재생성하거나 비우지 않습니다.
기존 control authorization/qualification이 필요하며, writer 변경에 의해 qualification
fingerprint가 바뀌면 정해진 자격 갱신 절차가 선행돼야 합니다.

`ha_cards/aqua-dosing-schedule.js`를 HA의 frontend module resource로 등록한 뒤:

```yaml
type: custom:aqua-dosing-schedule
entity: sensor.aquarium_dosing_schedule
```

센서는 MQTT Discovery로 등록되며 실제 entity ID가 이미 사용 중이면 HA가 다른 ID를
정할 수 있으므로 확인합니다. 기존 `custom:aqua-utility-card`의 도징 화면에 포함하려면
해당 카드 설정에 `dosing_schedule_entity: sensor.aquarium_dosing_schedule`을 추가합니다.
두 카드 module resource가 모두 필요합니다. HA `.storage` 파일을 직접 수정하지 않습니다.

## 구현 후 코드리뷰

검토 범위: 캘린더, 예약 actor, 기존 writer/journal 접점, MQTT 수명주기, HA 편집 UI.
리뷰에서 수정한 사항:

- 생성 시 읽은 상태를 실행 잠금 후 재사용하던 경쟁 조건: 잠금 후 영속 기록을 다시 읽음.
- 미래 기준일 및 DST 반복 시각 비교: UTC 기준 비교와 행별 검색 시작일 사용.
- 정리 후 정지 원인이 사라지는 표시: 별도 pause reason 보존.
- 예약 해제 중 재활성화 버튼: 소유권 해제 전 비활성화.
- 실행 중 템플릿 이름 변경: 실행본 이름을 고정하여 잘못된 실행본 표시 방지.

회귀 테스트는 스크립트된 포트와 coordinator fault injection으로 코드의 중복 송신 방지,
ACK 누락 후 재조회, deadline, restart, 파일 잠금 및 미계측 표시를 검증합니다.
브라우저 테스트는 저장/활성화 분리, 편집본 보존, revision 충돌, escape, 모바일 레이아웃을
검증합니다. 실제 장비 동작 확인은 별도 승인된 실기로 남습니다.

검증 결과: local-control 및 dosing 단위/회귀 테스트 1,645개 통과,
신규 도징 브라우저 테스트와 기존 utility 카드 테스트 통과, 변경 코드 Ruff 및
`git diff --check` 통과. 데스크톱과 모바일 렌더링도 로컬 테스트 화면으로 확인했습니다.
별도 리뷰 에이전트를 실행한 것은 아니며, 구현 후 코드 경로를 다시 읽고 회귀 테스트를
보강하는 리뷰를 수행했습니다.

자동 생성 추가 후 local-control·dosing 회귀 테스트 1,669개가 통과했고,
날짜 범위 오류 사례 추가 후 도징 관련 57개가 다시 통과했습니다.
유한 계획의 마지막 예약 해제 전 소유권 해제, 생성 요청 중 편집 revision 변화,
오래된 미리보기 재사용, 일반 복구가 지난 반복 예약을 되살리는 경로를 검토·수정했습니다.
모바일 입력칸 겹침은 실제 렌더링으로 발견해 수정하고 요소 경계 검사도 추가했습니다.
HA 실서버 미리보기 4개 조합과 실제 Orca의 1.5mL 미리보기까지 확인했으며,
이 검증에서 저장본·실행본·장치 예약은 만들지 않았습니다.
